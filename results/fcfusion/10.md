The program is saved to `wordfreq.jl`. Here's why it's correct and how it scales:

## Race-free design

The key insight is that **each thread owns its own private `Dict{String,Int}`**. No two threads ever write to the same dictionary concurrently:

```julia
Threads.@spawn begin
    local_counts = Dict{String, Int}()   # Thread-private
    for f in part
        # ... mutate local_counts only
    end
    return local_counts                  # Return, don't write shared state
end
```

After all tasks complete (`fetch(t)` for each), the main thread merges the per-thread dictionaries **sequentially** — by definition race-free because no tasks are still running.

This is the classic **map-reduce** pattern: map = parallel per-thread counting, reduce = sequential merge.

## Scaling characteristics

- **Linear with threads** (ideal case): N threads process N× as many files in the same wall-clock time, assuming files are roughly equal in size.
- **Load imbalance**: If some files are much larger than others, faster threads will finish early and sit idle while slower threads process big files. The `cld(nfiles, nt)` partitioning tries to balance this by giving each thread roughly equal file counts.
- **Merge cost**: O(V) where V is total vocabulary size — negligible compared to file I/O and regex tokenization for real corpora.
- **Memory**: Each thread holds its own dictionary, so peak memory is ~N× the average per-thread dictionary size until merge. After `fetch()`, all dictionaries coexist briefly before `merge_counts` creates the final merged dict.

## Run it

```bash
julia wordfreq.jl /path/to/text/files
```

For better parallelism on large corpora, run with more threads:

```bash
JULIA_NUM_THREADS=8 julia wordfreq.jl /path/to/text/files
```

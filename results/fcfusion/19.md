All tests pass and the benchmark shows ~130k puts/sec (well under 1s for 10⁵). Here's the implementation:

## File Format

Each record is:
```
[magic:4][flags:1][key_len:4][val_len:4][key][value][crc32:4]
```
- **magic**: `0x4B565354` ("KVST") little-endian, identifies record boundary
- **flags**: bit 0 = tombstone (deleted)
- **key_len/val_len**: uint32 little-endian
- **crc32**: CRC32 over magic+flags+key_len+val_len+key+value (not the CRC itself)

Records are appended sequentially. The file is a simple log with no fixed-size slots or free-list.

## Crash Recovery

On `open_store()`, the file is scanned forward. Each record's CRC is verified. The first record with a bad CRC, wrong magic, or that doesn't fit in the remaining file is considered torn/corrupted — it and everything after it is discarded. This handles crashes mid-write naturally.

## Design Choices

- **In-memory index**: `Dict{String, Int}` mapping keys to the byte offset of their latest record. `get` is O(1) — just seek and read.
- **Deletes as tombstones**: `delete!` writes a tombstone record (empty value, flag set) and removes the key from the index. The old record remains in the file until `compact!`.
- **Compact**: rewrites the file with only the latest non-tombstone records, replacing the original via atomic rename.
- **No fsync on every write**: `flush()` pushes data to the OS buffer cache. Durability comes from the torn-record detection on reopen, not from synchronous disk writes. This is what enables the high throughput.

## Benchmark Results

- 100,000 puts: ~0.75s (134k puts/sec)
- 10,000 gets: ~0.03s (333k gets/sec)
- Compact reduces file from 524B to 252B (removes superseded records)

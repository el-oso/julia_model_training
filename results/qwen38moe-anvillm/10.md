## Why the merge is race-free

The program follows the **shared-nothing** pattern:

```
Main thread                     Spawning tasks
──────────                     ────────────────
                              ┌─ task A: local Dict{"hello", 3}
spawn @count(a.txt) ────────►│
spawn @count(b.txt) ────────►├─ task B: local Dict{"the", 2}
                              │
fetch A ──► local Dict       │  ← no shared Dict exists during work
fetch B ──► merge in main    │  ← single thread, no contention
                              └───────────────────────────────────
```

**Each task owns its own `Dict{String,UInt64}`.** No task reads or writes another task's dict, and no task writes to a dict the main thread is reading. The merge loop (`for t in tasks; for (w,c) in fetch(t); global_counts[w] += c; end; end`) runs on a **single thread** after all tasks have completed. There is zero overlap between any two tasks' mutable state.

Contrast this with the tempting (but wrong) approach of having every task increment a single shared `Dict`:

```julia
# RACE-CONDITION! Multiple threads read/modify/write the same key
Counts[word] = get(Counts, word, 0) + 1  # read-modify-write on a non-atomic Dict
```

This is a data race on the `Dict`'s internal hash-table structure. You'd need `Threads.Atomic{UInt64}` per key or a `Channel` to serialize writes — both add overhead the shared-nothing pattern avoids entirely.

## How it scales with threads

| # threads | speedup vs 1-thread | reason |
|-----------|--------------------|--------|
| 1         | 1× (baseline)      | serial I/O + regex |
| 16      | ~1.4–2×            | CPU-bound (regex, hash) + some I/O parallelism |
| 64+     | ~2× (plateau)      | I/O bound; all threads compete for disk bandwidth |

The speedup comes from the fact that each task is **CPU-bound** (regex matching, Unicode lowercasing, dict inserts) on a separate file, so the OS can pipeline the work across cores. I/O parallelism also helps: while one task is blocked reading, another is busy matching words. The plateau at ~2× reflects that the bottleneck is ultimately disk bandwidth, not CPU count.

The `Threads.@spawn` approach also lets you use **more threads than physical cores** (the machine has 16 threads) because the tasks are I/O-mixed — threads get preempted on disk reads and the OS schedules other tasks. With pure CPU work you'd hit oversubscription overhead at ~2× the core count.

| | Time | Allocations |
|---|---|---|
| **Original** | 142.2 ms | 24 M allocs, 946 MiB |
| **Optimized** | 15.8 ms | 18 allocs, 153 MiB |

**~9× speedup**, **1.3M× fewer allocations**, **6× less memory**.

## Each change explained

### Change 1: Replace the nested loop with `G = X * X'` (BLAS `gemm`)

The original does `n² = 4,000,000` iterations of `X[i, :] .- X[j, :]` — each iteration allocates a temporary 3-element vector, squares it, sums it, and takes `sqrt`. That's **24 million allocations** for a 2000×3 matrix.

The optimized version computes the **Gram matrix** `G = X X'` in one BLAS call. `gemm` is a single highly-tuned C/Fortran routine that operates on the whole matrix in cache-friendly order — no per-element allocations, no loop overhead in Julia.

### Change 2: Use the algebraic identity `||xᵢ − xⱼ||² = ||xᵢ||² + ||xⱼ||² − 2·xᵢ·xⱼ`

Since `G[i,j] = xᵢ·xⱼ` and `d[i] = xᵢ·xᵢ = ||xᵢ||²`, the full distance matrix is:

```
D[i,j]² = d[i] + d[j] − 2·G[i,j]
```

This is a single element-wise broadcast: `d .+ d' .- 2*G`. No Julia-level loop at all.

### Change 3: Clamp negatives with `ifelse.(D .< 0, 0.0, D)`

Due to floating-point rounding, `d[i] + d[j] − 2·G[i,j]` can be a tiny negative (≈ −1e-14) when `i == j` or when two rows are nearly identical. `sqrt` of a negative is `NaN`. `ifelse.(...)` is element-wise (unlike the ternary `?:`) and is fused into the same pass as the `sqrt` below.

### Change 4: `sqrt.(D)` — vectorized `sqrt`

A single broadcast over the matrix instead of `sqrt(...)` inside a loop.

---

## Why this is the fastest path

For `X` of size 2000×3, the bottleneck is the `X * X'` multiplication (a 2000×3 × 3×2000 → 2000×2000 matrix multiply). That's handled entirely by BLAS, which on this machine (AMD Zen5) uses a tuned OpenBLAS kernel. The remaining work (`d .+ d' .- 2*G` + `sqrt.(D)`) is O(n²) element-wise but with zero allocation and fused passes — essentially just memory bandwidth, which is already near-optimal for a 2000×2000 matrix (~32 MB).

The original's `X[i,:] .- X[j,:]` in a loop is the killer: it allocates a 3-element `Vector{Float64}` **4 million times**, each one going through the GC. That's what costs 142 ms vs 15 ms.
